the harness · cumulative testing guide

Everything to test, in one place

One document that grows with the build. Each milestone appends its own section and nothing is ever removed, so a case you already signed off on stays here as a regression check. Cases an automated gate has already driven against a real server with a real model are marked as such — those you can skim; the unmarked ones are where your eyes are actually needed.

How to read the markers

Marker Means
verified live An automated gate sent this prompt to your dev server on :3051 with your real OpenAI subscription model and asserted the durable outcome — runs, journal, plan, transcript. The date and one line of what actually happened are given.
verified headless The mechanism was driven directly on the branch code — no model, no UI. Proves the plumbing, not the experience.
not live-verified Covered by unit or integration tests only, or not reachable from the build that was running. Needs a human.

Where everything is

~/Code/Seed                      ← harness/01-verbs             M1 · running on :3051
~/Code/Seed-worktrees/harness-02 ← harness/02-tools-as-docs     M2 · done, reviewable
~/Code/Seed-worktrees/harness-03 ← harness/05-exec              M3 + UX + M4 + M5 + M6 bus (stacked)

The branches are stacked — M2 sits on M1, the UX package sits on M3 — and only one of them can be the running server at a time. That is why the live-verified marks cluster in M1: it is the build that was up all night. Nothing is pushed.

Launching a build

# from the checkout you want to test — desktop spawns/connects its local agents server
pnpm install && pnpm desktop

# or run the agents server standalone with hot reload
cd agents && pnpm dev

The first message to an existing agent replays its old transcript against the new verbs. Old tool names in history render generically and never re-execute, but a fresh test agent gives the cleanest read.

Feedback

Tell Claude in the session, or drop notes into agents/docs/harness/reviews/<milestone>.md in the matching worktree. Fixes land as commits on the milestone branch and rebase up through the stack.

M1 · The five verbs running on :3051

The 25-tool registry is gone. The model holds five always-on verbs — read, write, call, delegate, plan — and everything else is dispatched through call. One delegation verb replaces sub_session / run_workflow / start_session; memory, IPFS, attachments, the activity feed, and hypermedia publishing are address forms of read/write.

  • The file appears on the agent's Memory tab.
  • Stronger version: ask in one thread, then open a new thread with the same agent and ask “what is my favorite database?” — it should read memory rather than guess.

M5 · Time harness-03 · harness/05-exec

A run can now wait for something to happen without holding a worker: ctx.waitForEvent parks it until a matching activity event or an explicit signal arrives, ctx.continueAsNew ends a run and starts a successor carrying only the state it declared, and a run that outlives its time budget pauses for a person instead of failing.

M5.1 · A run that waits for you

Use a script child that publishes nothing until I approve it: have it wait for a signal called “approved” with the label “sign-off from Eric”, then write what it got to ~/memory/approval.md.
  • The run card does not spin — it parks, and says what it is waiting for: sign-off from Eric rather than a bare “Waiting”.
  • The run holds no worker slot while parked; other work in the session proceeds normally.
  • Sending the signal wakes it exactly once, and the payload you sent is what the script receives. A second signal delivers nothing — the run is no longer listening.
  • Restart the server while it is parked: it is still parked, still listening, and the signal still works.

How you answer it. The parked card carries the button: Answer sends the signal the run named and wakes it immediately. If it wants data back, Answer with data opens a small JSON field first — leave it empty and it is the same one-click answer. A run paused on its budget shows Resume instead. If the run moved on while the card sat open, you get “This run is no longer waiting for that” rather than a silent no-op.

Two cases deliberately show no button, and that is the feature working: a run waiting on its own children, and a run watching the activity feed. Neither is asking you for anything — they resolve themselves — and a button there would send a signal the run ignores.

not live-verified — verifies headless in agents/src/run-time.test.ts, which drives real workflow runs through the real queue: the park survives a restart (a fresh service on the same database), one signal wakes it, the journal holds exactly one delivery, and a second signal is refused. The exactly-once property is structural — the journal write and the requeue are one SQLite transaction — so a signal that loses a race writes nothing at all.

M5.2 · A wait that gives up, and a signal that arrives too late

Same thing, but tell it to give up after two minutes and write “no answer” instead.
  • The card shows the wait with its deadline (“… (until 4:15 PM)”).
  • When the deadline passes the run resumes on its own and takes the give-up path.
  • A signal sent after that is not delivered: the decision has already been made.
not live-verified — run-time.test.ts asserts the timeout resume and the refused late signal; workflow-host.test.ts asserts the opposite race too (a payload that won in the database beats a deadline that has since passed, because the journal — not the clock — is the record of what happened).

M5.3 · A run that hands itself on

Use a script child that processes one item per generation and calls ctx.continueAsNew with the next index, for three items.
  • Each generation finishes as its own run, and the next one starts carrying only the state it was handed — a fresh journal, not a growing one. This is what lets a loop run for weeks.
  • The generations are linked: the finished run's result names its successor, and the successor names its predecessor.
  • If the loop was started by a delegate call, that call is answered by the last generation, not the first. A continuation is the same work, not a finished one.
not live-verified — run-time.test.ts asserts the state handoff, the link in both directions, and that the successor's journal has its own entries and none of its predecessor's.

M5.4 · A run that pauses on its budget

Give a long-running script child a wall-clock budget (a workflow run carries one), and let it outlive it.

  • The status pill reads Paused, not “Waiting”, and the card says Paused: out of time budget. This is the one wait a person has to end, so it does not hide behind the same word as a sleep.
  • The clock will never release it — nothing wakes it but you.
  • Resume on the card lets it finish. The limit that stopped it is dropped, not deferred: a resume that re-pauses on the next tick would be a button that does nothing.
not live-verified — run-time.test.ts drives a run past its budget, asserts the wait shape and that it has no wake time, releases it with a signal, and checks it finished with the limit gone.

M6 · The event bus, first slice harness-03 · harness/05-exec

The bus underneath the trigger surface. Two things a trigger could not do before: fire when a run finishes, and answer a run that is already waiting instead of always starting a new thread. The trigger surface itself is untouched — trigger documents, the draft→active consent step, the migration and the protocol deletion are a day package, argued in agents/docs/harness/m6-event-bus-design.md.

Creating one is API-only for now. The desktop renders a run-completed trigger — summary line and icon — but has no form for making one, because the form belongs with the trigger document editor that lands with the day package. Until then these cases are driven the way the live gate drives everything: a signed CreateAgentTrigger envelope.

M6.1 · One automation starts the next

Create a trigger with source {type: 'run-completed', status: 'succeeded'} and continuation {kind: 'wake', signal: 'go'}. Start a script child that waits:

Use a script child that waits for a signal called “go”, then writes what it received to ~/memory/unblocked.md.

Then let any run of that account finish.

  • The waiting run wakes on its own — nobody clicked anything — and receives the delivery.
  • What it receives says where it came from: source: 'trigger', distinct from a hand-sent signal and from an activity event. Same delivery path, honest about its sender.
  • Exactly one delivery lands in the woken run's journal, however many times the trigger matched.
not live-verified — verifies headless in agents/src/trigger-events.test.ts, which drives real runs through the real queue and the real finalizer: a parked run, a second run finishing, the trigger firing, and the first run resuming with woken by trigger.

M6.2 · A trigger that fires into an empty room

Same trigger, but with nothing parked on that signal. Let a run finish.

  • Nothing breaks and nothing is silently swallowed: the firing is recorded as no-listener. The firing history is what you debug a trigger with, so a firing that found nobody has to be visible.
not live-verified — asserted in trigger-events.test.ts.

M6.3 · The loop that does not happen

A run-completed trigger whose own continuation produces a run is one step from an infinite loop: its run finishes, which fires it again, forever. Point one at itself and let it run.

  • It fires once. The run it caused does not cause it again.
  • The guard walks back through the firings that produced each run — so a two-trigger cycle (A fires B, B fires A) is caught as well, and any chain deeper than eight hops is treated as a loop whether or not it repeats.
not live-verified — trigger-events.test.ts proves it with a forged chain: a run that exists because the trigger fired does not re-fire it.

M6.4 · What the source can watch

run-completed filters on the agent, on how the run ended, and on a case-insensitive substring of its title — so “when the nightly digest finishes” is expressible without watching every run on the account.

  • A trigger watching status: 'failed' stays quiet when a run succeeds, and vice versa.
  • A trigger watching another agent's runs never fires for yours.
  • titleMatch: 'nightly' matches a run titled “Nightly crawl”.
not live-verified — the four-way matrix is asserted in trigger-events.test.ts.

The live gate

agents/e2e/live-gate.ts is the script behind every “verified live” mark. It is a pure client: it signs action envelopes with your Seed daemon's key over grpc-web — the same path the desktop app uses — and talks CBOR to an already-running agents server. That is what lets it gate the build you are actually using, with your real subscription model, rather than an in-process service replaying recorded responses (which is what agents/e2e/run.ts does).

It creates its own throwaway agent named NightGate, mirroring the provider, model and toolset of an existing agent so it tests your real setup. It writes full transcripts, run trees, journals and child threads to the artifact directory, then deletes the agent so your sidebar stays clean. 

# everything, against localhost:3051
cd agents && bun e2e/live-gate.ts

# one scenario, keep the agent around to poke at it in the UI
bun e2e/live-gate.ts parallel-delegate --keep --out /tmp/gate

# a different build on a different port
bun e2e/live-gate.ts --base http://localhost:3099
Scenario Asserts
trivial One run, no delegation, the answer, and a model-authored session title.
memory Write verb to ~/memory/, the file present via ListAgentMemory, and recall of an exact codeword from a second session.
parallel-delegate Two children with declared output schemas, a settled plan, the parent observed waiting · children, typed payloads, two nested threads, a combined answer, no child spawned twice, and — the part that catches silent breakage — every child carrying a planStepId that still resolves in the final plan. Same-turn fan-out and child overlap are reported, not enforced: this model delegates serially no matter how the contract is worded, so failing on it would only restate a known behavior.
script-parallel A script child whose two ctx.parallel children genuinely overlap, and the combined memory file.

Park/resume is asserted from what the poller witnessed, not from the final row: a run that only ever shows succeeded at the end is indistinguishable from one that never parked. Same reasoning for fan-out — only the transcript shows whether two children were one reply or two.

agents/e2e/narration-check.ts is the headless companion: it drives the workflow VM with a stub adapter, so the narration mechanism is gated on any branch without a model, a server, or credentials.

Attachment survives a rename verified live

A child is hung under its plan step by step id, not by the step's label. This matters because agents rewrite their step labels constantly, mid-task, without being asked.

verified live ✓ (2026-08-12 night), twice — in two separate runs the model renamed its running step while its children were working. Both children kept planStepId: "s1", which still resolved in the final plan, while their stamped labels ("Research SQLite and PostgreSQL in parallel") matched no step at all. Under the previous label-based join both children would have detached and rendered as loose rows below the checklist — the bug this case now guards.

If you ever see a sub-agent row floating beneath the checklist rather than attached to the step that spawned it, that is this bug returning, and the gate should have caught it.
