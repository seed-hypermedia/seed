---
name: Document apps
summary: A document whose `app` attribute names a UnixFS folder with an index.html opens as that app, sandboxed, and reads, writes and signs Hypermedia as the viewer through a host-owned bridge with progressive read and signing approvals.
---
A **document app** is a [document](../protocol/documents.md) that carries a web app. Its [metadata](../metadata.md) has an `app` attribute, an `ipfs://<cid>` that names a UnixFS folder whose `index.html` is an app. Web-compatible bundles inline their scripts, styles and images; desktop-only bundles can use relative asset files. When the document is opened in Seed, the app fills the main view without document margins, header, tabs or footer. Breadcrumbs and the document browser remain. People, Comments, Citations and Attributes open from the breadcrumb options menu as panels beside the app. Editing still shows the underlying document. The folder is a file the document references, so it syncs with the document: share the document and the app arrives with it. <!-- id:4p_wlxmi -->

An agent builds such an app with the ordinary [`write` verb](../agent.md): it writes the HTML under its memory and then writes a document with `options.app` naming that folder (or single HTML file). The folder is published to IPFS as a UnixFS directory in the same publish as the document change, and the document's `app` attribute points at it. The write result tells the agent to share the document's `hm://` URL, which opens the full app view. App execution inside chat is temporarily disabled; older `seed-app` fences render an Open app link. There is no separate app tool and no app that is not a document. <!-- id:s4mOJM7z -->

# Data before UI <!-- id:6DfnJi96 -->

For apps with durable user data, agents must define or reuse HM schemas, establish schema-bound Seed resources, and then build the interface to the user's specifications. A task tracker should have a Task type document (`schemaDefinition`), a task collection (`childAttributesSchema`) and individually editable task documents (`attributesSchema`, name, status and the requested fields). Store real collection/type URLs in the app's metadata. The data remains available through ordinary Seed documents and other apps, independently of the HTML bundle. <!-- id:IqUmyUJo -->

The agent's `~/tools/write/apps` guide supplies the workflow and an executable task data adapter. `seed.directory` and `seed.resource` read records; `seed.publishDocument` creates and edits them using the current viewer's authority. Updates preserve the document's genesis/generation and use its current base version. Establish the intended user/shared data space, privacy and write access during setup; an agent-owned collection that the user cannot edit is not a completed app. <!-- id:LcAwU0H8 -->

Use `seed.storage` only for optional device-local UI preferences or temporary unsaved drafts, unless the user explicitly requests local-only primary data. Never substitute local storage when a Seed read/write fails or is denied. Existing local records need an explicit migration that preserves the originals until publication/read-back succeeds. Stateless apps do not need artificial schemas. <!-- id:r-6CxFKU -->

Verify create/read/update and reopen with local state empty, then read the same record through ordinary Seed tools. Distinguish that persistence test from a cross-host sync test. Publication receipts report `dataPersistenceTested: false` because syntax/asset checks cannot establish a working data layer, even if the source mentions Seed write methods. <!-- id:R4XFSnY0 -->

# What the app may do <!-- id:sEBfqfoQ -->

The app is untrusted code: once a document is shared, someone else's app runs on the viewer's machine beside the viewer's data. So the app runs in an origin of its own, with no network, no access to the daemon or its secret, and no access to the Seed window. Desktop permits assets from the app folder. Web uses an opaque iframe and HTTP CSP sandbox on the same Seed origin; inline scripts/styles and embedded images are supported. Use self-contained HTML for both platforms. Sandboxing does not guarantee that data disclosed to app code cannot leave it through navigation. <!-- id:MyRnFAuR -->
  - **Origin.** The desktop serves the folder at `seed-app://<host>/`, where the host is a fresh unpredictable value for each launch, bound to the canonical document, immutable bundle CID and selected viewer. Opening a different revision cannot replace assets served to an already-open revision. Native storage starts fresh on each launch and is cleared when the owning window closes or releases it; it cannot silently carry previously disclosed data into another launch. Optional device-local UI state uses `seed.storage.get/set`, whose host-managed namespace is `(viewer account, canonical document HMID)`, independent of the app revision. Different resources never share that state, even if their HTML is identical. <!-- id:qkgetBC6 -->
  - **Bridge.** The app includes `<script src="/.seed/client.js"></script>`, which defines `window.seed`. Except for the synchronous display helper `seed.stringify`, each method posts a request to the Seed window that embeds the app and resolves with its answer; the Seed window answers the allowed calls. Web installs the API before app code runs and ignores the desktop bridge include. Both platforms gate identity, content and saved-state reads through Seed-owned approval UI. <!-- id:Q1Xrhos_ -->
  - **SDK.** `seed.context()` returns `{protocol: 1, document, version, account, app}`; `account` is the selected viewer UID or null, not `viewer`. `seed.profile()` returns `{id, name}` for that viewer or null when signed out. Use `const profile = await seed.profile(); heading.textContent = profile?.name ? "Hello, " + profile.name + "!" : "Hello, friend!"`. Profile data comes from the Account API, not a document at `/:profile`; that URL is supported as a compatibility alias for the selected viewer. Handle SDK errors separately from signed-out state. `seed.resource(hmUrl)` reads documents, including the app document, after approval. `seed.directory(hmUrl, {all})` also requires approval on both platforms. `seed.storage.get(key)` returns saved JSON or null; `seed.storage.set(key, value)` persists JSON (64 keys, 128 characters/key, 16 KiB/value). Reading, signing and publishing have independent rules described below. <!-- id:W8d7Tl95 -->

# Account access, writes and signatures <!-- id:YSnzkVRV -->

Mini apps use a host-owned facade over `@seed-hypermedia/client`, on both desktop and web: <!-- id:LB_GsYHp -->

```js <!-- id:4euGDfTy -->
const content = await seed.hm.parseMarkdown(messageInput.value)
const {commentId, version} = await seed.comments.create({content}) // Seed reviews the signature
```

`seed.hm.parseMarkdown` returns HM block nodes with IDs and annotations. `seed.hm.validateContent(content)` validates app-constructed block nodes. Both are asynchronous, use the existing SDK in the host, and have no signing side effects. `seed.hm.unpackHmId(url)` parses HM URLs. Requests are limited to 8 MiB including binary bytes, with at most 32 pending calls. <!-- id:FtuStJku -->

Running an app is separate from granting it access. Apps from joined sites, your own site or the current web site's identity run automatically. Other sites show **Run app**, explaining that code can mislead, consume resources and open links. Joining is optional. Execution alone exposes no selected identity, document content or saved app state through the bridge. <!-- id:srhIdCrl -->

The first operation needing access opens a Seed-owned review, defaulting to **Allow once**. **Allow more like this** offers narrower remembered rules alongside all-reading, any-signing or all-publishing, independently. These broad permissions require an extra acknowledgement, without another disclosure to reveal them. Comment reviews show the text and target site; exact payload details and a SHA-256 fingerprint are available. Rules are remembered for `(selected viewer, canonical app document ID)` on this device, including future code updates. Optional version-pinned permissions are future work. <!-- id:SDHt-XnV -->
  - **Reading:** approve a resource, a site, or all reads. Identity/profile/public-key access and saved app data need their own read approval. Search, directory queries, comments and other results with an unbounded cross-site footprint currently offer once or all-reading; they cannot silently inherit a site grant. Resolved document targets are checked again before disclosure. <!-- id:Jm0jcobp -->
  - **Signing:** approve one signature, an established signature type on one site, that type everywhere, or any signing. Comment creation, comment edits/deletions, document changes, references, contact changes and lasting capabilities are distinct. Classification validates the canonical signing bytes and actual signing principal against the protocol schema; the app cannot choose a label to obtain broader access. Types without a provable site binding have no site option. Unrecognized payloads offer only once or any-signing. <!-- id:0RMtjjbQ -->
  - **Publishing:** exact recognized envelopes signed and approved in this launch may be published without another prompt. Modified blobs, extra attachments and previously signed/imported payloads need publication consent. Generic `PublishBlobs` requests use the same check. <!-- id:qZL-0mVf -->

`seed.permissions.request()` returns `{grants}` without granting anything. **App permissions** in the breadcrumb menu lets the viewer inspect, revoke individual rules or reset all to ask; `seed.permissions.revoke()` resets the app's rules too. Revocation also aborts active/queued calls and propagates to other open views on the same origin. Closing, changing account or changing code cancels in-flight calls while keeping remembered rules. Allow-once approvals never coalesce different operations. <!-- id:__iSnD5h -->

An app can exfiltrate data after you disclose it: the sandbox limits ambient browser authority, not what the app can do with data it receives. Reading and signing are therefore independent. Keys remain in Seed. Revocation cannot recall disclosed information, completed signatures, publications or lasting protocol capabilities already issued. <!-- id:ICIxoM5i -->

The asynchronous APIs are identical on web and desktop: <!-- id:-PeUsTvd -->
  - `seed.request(key, input)` exposes all requests in the SDK's `HMRequest` union with schema-validated inputs. `seed.resource(url)` and `seed.directory(url, {all})` are convenience reads. <!-- id:JEL8XDJg -->
  - `seed.publish({blobs: [{cid, data}]})` publishes arbitrary blobs; `data` is a `Uint8Array`. `seed.publishDocument({account, path, changes, baseVersion?, genesis?, generation?, capability?, visibility?})` prepares, signs and publishes protobuf document operations. `account` is the target space; signing always uses the selected viewer. <!-- id:Gy79meik -->
  - `seed.signer.getPublicKey()` and `seed.signer.sign(bytes)` implement `HMSigner`, for an SDK bundled inline into the app. The app receives public-key/signature bytes, never private keys. Web sign-in may use a delegated device key whose signing principal differs from the selected account; the protocol still enforces its delegation. <!-- id:hI7cG6fU -->
  - `seed.hm` provides the SDK's `createComment`, `updateComment`, `deleteComment`, `createDocumentBlobs`, `createVersionRef`, `createRedirectRef`, `createTombstoneRef`, `createCapability`, `createContact`, `updateContact`, `deleteContact`, `signDocumentChange` and `signBlob`. Each accepts its SDK input without a signer argument. Signing helpers return their SDK result without publishing (`signDocumentChange.changeCid` is serialized as a string); `signBlob(body)` returns `{cid, data, ts, signer}` for a custom dag-json blob body. <!-- id:3q0DXpCt -->
  - `seed.comments.create({content, target?, version?})` signs and publishes in one call. By default it comments on this app's document at the displayed revision; another target needs a version, and visibility follows the target. It returns `{commentId, version}`. <!-- id:bU8KLCs3 -->

For a new document, use the SDK's document builder and publish the resulting signed blobs: <!-- id:a6FBSsSF -->

```js <!-- id:SqtVqNUo -->
const {account} = await seed.context()
const {blobs} = await seed.hm.createDocumentBlobs({
  space: account,
  path: '/apps/data',
  ops: [{type: 'SetAttributes', attrs: [{key: ['name'], value: 'App data'}]}],
})
await seed.publish({blobs})
```

Use versioned document changes for edits, rather than recreating an existing document. Keep Submit disabled while an operation is pending, preserve input on denial/error, and clear it only on success. Remembered grants survive app instances and code updates; broader permissions do not merge apps' local storage namespaces. Protocol permissions still govern what the selected account may change. <!-- id:hlf7GHeT -->

# Linking and runtime compatibility <!-- id:17tMApB7 -->

Use ordinary anchors such as `<a href="hm://<account>/notes?v=<version>#<block>">Notes</a>` or `await seed.open(url, {newWindow: false})`. The host opens Hypermedia links outside the app frame. Explicit HTTP(S) links retain their server, query and fragment instead of being rewritten to the current site. `_blank`, modifier clicks and middle clicks request a new tab/window; browser popup rules still apply. Unsupported schemes and credential-bearing URLs are rejected. Catch SDK errors to preserve app input; host navigation errors also appear as notifications. Anchor failures dispatch `seed-link-error` on the app window. Navigation needs no account-access grant. <!-- id:MgUiUh_j -->

SDK 1.2.0 reports `authority: "scoped-app-permissions"`. SDK 1.1.0 introduced `await seed.runtime()`: the running SDK version and implementation digest, supported bridge methods, platform, limits, authority and storage semantics. Check for the method before calling it on older hosts; a guide or source checkout does not prove that a running host has been updated. `seed.stringify(value)` formats SDK BigInts and byte arrays for display, not signing or round-trip serialization. <!-- id:7IHH63oo -->

Publishing with `write(..., options: {app: ...})` defaults to `appTarget: "web-desktop"`. It parses JavaScript without executing it and rejects unsupported external assets or module scripts before publishing. Use inline classic scripts, styles and data images. `appTarget: "desktop"` explicitly permits bundled asset files. The write receipt includes `appValidation`, bound to the bundle CID, with syntax results and `runtimeTested: false`, `interactionTested: false`, `dataPersistenceTested: false`. These static checks do not prove startup or behavior; generated, syntax-checked, published, read back, opened and interaction-tested are distinct outcomes. Dry runs do not publish. Agents must read back publication state before retrying a failed operation and must never describe `seed.storage` as cross-device sync, backup or encrypted storage. <!-- id:6idmCJKm -->

Automation can invoke `InvokeSessionTool` with `continueAgent: false` to retain the tool result in the session journal without starting a model turn. The default remains true. `resultEventId` identifies the recorded outcome; this is not an idempotency guarantee for retries. Durable storage commits are serialized before reserving their sequence number, preventing concurrent writes on one storage instance from preparing conflicting journal positions. This does not repair previously corrupted journals. <!-- id:sELqTuvL -->

Reading and signing controls are implemented; optional version-pinned trust, undo/rollback, automated authoring-time startup/interaction validation, and migration of previously broken journals remain separate work. <!-- id:Yitj3bxi -->

# Where the pieces are <!-- id:wbK6irDo -->

- **Daemon.** `GET /ipfs/{cid}/{path}` walks a UnixFS directory the way an IPFS gateway does, types entries by extension, and serves a folder as its `index.html` (`backend/hmnet/filemanager.go`). The web app's `/hm/api/file/<cid>/<path>` proxies the same. <!-- id:pHJnvTPq -->
- **Shared.** `@shm/shared/document-app` holds the scheme, bridge, `DocumentAppSDK` TypeScript interface and message guard. `document-app-content` uses the HM SDK for block helpers and permission-controlled account requests and SDK signing; `document-app-permissions` classifies actual bytes and manages revocable scoped rules; `directoryToIpfsBlobs` in `@seed-hypermedia/client` builds the folder's blocks. <!-- id:9Pr7yzT- -->
- **Desktop.** `app-document-apps.ts` registers the scheme and serves app files from the daemon; `app-window-policy.ts` admits app frames; `DocumentAppView` in `@shm/ui/document-app` embeds the app and answers the bridge. <!-- id:WPSC9ID0 -->
- **Chat.** App embeds are temporarily disabled in the Markdown renderer. Legacy `seed-app` fences open the full document view through a link; the agent prompt and write result no longer emit embed fences. The reusable embed component is retained for a future return to inline apps. <!-- id:I8baoO6i -->
- **Web.** Normal document URLs render apps using `/hm/app-runner` on the same hostname/port. `/hm/api/app` checks that the requested bundle belongs to the readable document revision, then returns HTML as inert data. The parent transfers it through a launch-bound MessageChannel into the opaque sandbox. No wildcard DNS, per-app domains or separate runtime service are required. Raw `/hm/api/file` responses are sandboxed without scripts to prevent direct navigation from executing uploads with Seed authority. <!-- id:FbM8tviL -->

# Local web sandbox prototype <!-- id:KsQP6ACj -->

Run the normal web app with `direnv exec . pnpm web`, then open the document at `http://localhost:3000/hm/<account>/<path>`. The daemon must already be running as usual. No workshop server is needed. For the same-origin runtime's Chromium, Firefox and WebKit regression tests, run `direnv exec . node --test frontend/apps/web/scripts/document-app-browser.e2e.mjs`. These test storage isolation across viewers/resources/revisions, public profile resolution, account-bridge transport, native storage/DOM/fetch blocking, late-result revocation, and direct runner visits. <!-- id:FpokQ7ZJ -->

The earlier workshop in `scripts/document-app-demo/` is retained as an experiment; ports 53110/53111 are not part of the integrated runtime. Web apps currently require inline scripts/styles, embedded assets, and click handlers rather than form submission; relative asset files are not implemented. The workshop uses its own experimental permission model; the integrated runtime uses the progressive permissions described above. Local state is browser-local, not synced or encrypted, and updated app code inherits that resource's remembered rules; reading existing state requires read approval. The prior workshop's navigation probe demonstrates that blocking fetch does not prevent every data leak. <!-- id:HsssNQvy -->
